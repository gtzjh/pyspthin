# pyspthin Validation Core Hardening Design

Date: 2026-04-25

## Goal

Strengthen `pyspthin` as a robust Python library core for data engineering workflows. This design focuses on input validation, result metadata columns, row-level diagnostics, and tests. It does not add a CLI, batch configuration, or CI/coverage gates in this phase.

## Decisions

- Use a breaking upgrade. Existing output column names and implicit missing-value dropping can change.
- Remove `missing_policy` entirely.
- Default validation is strict. Invalid required data fails before graph construction or algorithm execution.
- Preserve user input columns exactly. `pyspthin` must not overwrite user columns.
- All columns generated by `pyspthin` use the `pyspthin_` prefix.
- Validation errors include row-level context: input row, field name, original value, and reason.

## Internal Columns

Generated result columns:

- `pyspthin_record_id`
- `pyspthin_replicate_id`
- `pyspthin_replicate_rank`
- `pyspthin_retained_count`
- `pyspthin_species`

These columns are always used, even when no user column conflicts exist. Existing user columns named `record_id`, `species`, `replicate_id`, `replicate_rank`, or `retained_count` remain untouched.

## Record ID Semantics

`record_id_col` is treated as an input source column only.

If `record_id_col` is provided:

- values from that column populate `pyspthin_record_id`
- missing, empty, or duplicate values raise a validation error
- the source column remains unchanged in output dataframes

If `record_id_col` is not provided:

- prefer a unique, non-empty candidate column from `OBS_ID`, `obs_id`, `ID`, or `id`
- otherwise generate stable IDs as `record-000000`, `record-000001`, and so on
- generated IDs are stored in `pyspthin_record_id`

## Strict Validation

Validation runs before graph construction. Invalid rows are not dropped.

Required validations:

- input data must be non-empty
- required columns must exist
- longitude and latitude must be numeric
- longitude must be within `[-180, 180]`
- latitude must be within `[-90, 90]`
- species values must be present and non-empty after string trimming
- explicit record IDs must be present, non-empty, and unique
- configuration seed must be a non-negative integer
- `thin(...)` accepts exactly one species

The `missing_policy` configuration option is removed from `ThinConfig` and all documentation.

## Validation Errors

Add a custom exception such as `PyspthinValidationError`.

The user-facing message should be concise and actionable:

```text
Validation failed with 2 error(s):
row 7, field LONG, value 'abc': must be numeric
row 12, field LAT, value 95.0: must be within [-90, 90]
```

The implementation may keep internal error records to build the message, but this phase does not require a public structured error API.

## API And Result Semantics

Public function names stay the same:

- `thin(...)`
- `thin_many(...)`
- `summary_thin(...)`
- `plot_thin(...)`

Result behavior changes:

- `ThinResult.record_id_col` is `pyspthin_record_id`
- `ReplicateResult.retained_record_ids` is populated from `pyspthin_record_id`
- `ThinResult.original_columns` contains only user input columns
- `best_dataframe` and every replicate dataframe include all original columns plus generated `pyspthin_*` columns
- `warnings` no longer represents dropped-row audit information, because invalid data fails before producing a result
- `thin_many(...)` uses the same generated column names for every species and no longer forces child runs to use `record_id`

## Testing Scope

Validation tests:

- non-numeric longitude and latitude report row, field, original value, and reason
- missing coordinates fail
- missing or empty species fails
- out-of-range coordinates fail
- explicit record IDs that are missing, empty, or duplicated fail
- negative seed fails during configuration validation
- pre-existing user columns with names such as `record_id`, `species`, and `replicate_id` are preserved

API and regression tests:

- retained IDs come from `pyspthin_record_id`
- output dataframes always include the original input columns
- generated metadata columns always use the `pyspthin_` prefix
- `thin_many(...)` has consistent output columns in `parallel_mode="rep"` and `parallel_mode="species"`
- serial and parallel reproducibility remains unchanged
- R reference regression continues comparing retained-count summaries, not old metadata column names

Property tests:

- retained points still satisfy the thinning distance threshold
- replicates remain sorted by retained count descending
- all generated columns start with `pyspthin_`
- no user input column is overwritten

## Documentation Scope

Update:

- `README.md`
- `wiki/usage.md`
- `wiki/compatibility.md`
- `wiki/development.md`

Documentation must state:

- all generated columns use `pyspthin_`
- validation is strict by default
- invalid required data fails before algorithm execution
- `record_id_col` is a source column and is not overwritten
- `missing_policy` has been removed
- this is a breaking change from the previous output schema

## Out Of Scope

- CLI entry point
- batch job configuration
- quality report files
- public structured error-list API
- CI matrix changes
- coverage gates
- lint/type-check gates
- benchmark gates
